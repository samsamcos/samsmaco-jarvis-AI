JARVIS System Guide

Full technical reference — how everything works, where everything lives, and how to extend it.

What is JARVIS

JARVIS is a self-hosted AI browser automation system. It runs entirely on your local network — no cloud dependency, no monthly SaaS cost. At its core it is a Python Flask server that connects together a set of AI models, a real Chrome browser, a VNC remote desktop, Telegram notifications, and a set of web interfaces you can access from any device on your network.

The name JARVIS reflects the intent: it is always on, always reachable, and can be given tasks in plain English. You type (or speak, via mobile) what you want. JARVIS works out how to do it — searching the web, filling in forms, extracting data, booking things — and reports back.

Unlike cloud AI assistants, JARVIS has a persistent browser. It remembers logins. It can hold a Google session open and reuse it. It runs in the background while you do other things, and notifies you (on screen, via Telegram, on the MITOS display) when it finishes.

🎯 What it can do today

Search the web using a real Gemini browser session · Open any site and interact with it · Run background jobs while you do other things · Receive webhook calls from n8n, Home Assistant, or any HTTP client · Show results on a MITOS physical display · Send Telegram notifications · Manage up to 5 separate Google/Chrome accounts · Accept commands from chat, mobile, popup overlay, or remote HTTP

The server handles all routing. When you send a message, it decides which brain to use, what browser actions to take, and where to send the result. You never interact with Chrome, the AI, or the display system directly — everything goes through http://192.168.0.8:8080.

Flask Server

The core of JARVIS is server.py — a Python Flask application that has been extended over time to cover everything the system needs. It runs as a background process managed by systemd (or started manually), always listening on port 8080.

It provides REST API endpoints, server-sent event (SSE) streams for live updates, static file serving for all the HTML pages, and background threads for long-running tasks. All the HTML pages in the system are just static files served by Flask — they call the API endpoints using fetch() in the browser.

Key server responsibilities

  • Task routing — receives a message, picks the right AI brain, runs browser steps, collects result
  • SSE streams — pushes real-time events to connected browsers (RC overlay, agent page)
  • Site & profile management — stores site configs in JSON, manages Chrome profile assignments
  • Webhook routing — receives named webhooks and routes them to the correct search engine/site
  • VNC control — launches Chrome on display :1 with the correct profile directory
  • Proxmox integration — starts/stops/suspends VMs, monitors idle time
  • Config management — reads/writes .env and JSON config files
To edit server behaviour: all logic is in /root/ai-browser/server.py. The file is large (~2700 lines) but well-sectioned with comments. Search for the relevant route or function name to find what you want to change.

AI Brain

JARVIS uses a multi-brain architecture. When a message arrives, the server tries each brain in order until one produces a useful result. This means it always falls back gracefully — if the web search brain fails, the LLM brain still answers.

Brain 0 — Gemini Browser Search

For queries that look like searches (keywords: flight, price, news, weather, latest, find, buy, deal, hotel, etc.), Brain 0 fires first. It opens a real Chrome browser, goes to gemini.google.com/app, types the query, waits for the response, and extracts the text. This gives real-time grounded answers — prices, live news, today's weather — that a static LLM cannot provide.

Brain 1 — LiteLLM Proxy

For general questions and planning, Brain 1 calls the LiteLLM proxy running at 192.168.0.3:3080. This proxy can route to Gemini API, OpenAI, Anthropic, or any other model depending on how it is configured. The default model is gemini-2.5-flash.

Brain 2 — Browser Automation (Playwright)

When the AI plan includes browser_steps, Brain 2 executes them using Playwright on the headless display :99. It can click, type, extract, screenshot, and navigate. Playwright uses persistent Chrome profiles so sessions (logins) are remembered between runs.

Chrome profile data is stored in ~/.config/google-chrome/. The profile directories are named exactly as Chrome names them: Default, Profile 1, Profile 2, Profile 3, Profile 4. When you log into a Google account in one of these profiles, Chrome saves the session cookies to that directory. Next time that profile is opened, you are already logged in.

Switching profiles works by gracefully closing Chrome (SIGTERM so it saves sessions), waiting for it to exit cleanly, removing the singleton lock file, then launching a fresh Chrome instance with --profile-directory="Profile N". Because Chrome is force-quit only as a last resort (after 4 seconds), session data is always preserved.

The Playwright browser used for automated tasks uses separate profile directories at /root/ai-browser/profiles/ — these are distinct from the VNC Chrome profiles and run on the hidden display :99.

VNC & Display System

There are two display layers in the system, serving different purposes.

Display :1 — TightVNC (visible desktop)

TightVNC runs on display :1, port 5901. This is the desktop you see in the VNC viewer inside the browser. When you click "Open Site" or "Open Login in VNC", Google Chrome opens here. You can interact with it — type passwords, click buttons, solve CAPTCHAs — and the session is saved. The VNC desktop is 1280×720.

Display :99 — Xvfb (headless automation)

Xvfb runs on display :99. This is an invisible virtual display used exclusively by Playwright for automated browser jobs. Jobs run here silently while you use the system normally. Screenshots from automated jobs come from this display.

noVNC — browser VNC viewer

noVNC (a JavaScript VNC client) is served at port 6082 via websockify. It translates the VNC WebSocket connection into a browser canvas. The URL http://192.168.0.8:6082/vnc.html?autoconnect=1&resize=scale gives you a full interactive desktop in any browser tab. The Browser and Sites pages embed this as an iframe.

x11vnc — no-password VNC bridge

A second VNC server, x11vnc, runs on port 5903 — also pointing at display :1, but without a password requirement. websockify at port 6082 connects to this no-password server. This is what allows the embedded noVNC iframe to connect automatically without a login prompt.

Webhooks

Webhooks let any external system send a search query to JARVIS with a simple HTTP POST. No UI needed — just send JSON to a URL and the result arrives in Telegram and the overlay.

The base pattern is: POST http://192.168.0.8:8080/webhook/[site-id]-search with body {"message": "your query"}. For example, /webhook/gemini-search uses the Gemini web browser, /webhook/amazon-search opens Amazon and searches there.

Profile-specific webhooks let you target a particular Chrome profile: /webhook/profile1/gemini-search runs the search logged into Profile 1's Google account. This is useful if you have different Google accounts with different Gemini plans or search histories.

Webhook results are pushed to the RC overlay (visible on all connected screens), sent to Telegram, and optionally POSTed to a reply_url you include in the request body.

Agent — Main Chat Interface

The main page at http://192.168.0.8:8080 is the primary way to interact with JARVIS. It has a chat input, a results panel, a right-side panel with tabs (Output, Screen, Worker), and a navigation sidebar.

Type any question or instruction. For search queries, JARVIS uses Brain 0 (Gemini browser) to get live results. For tasks requiring browser automation, it builds a plan and executes browser steps. Flight results are rendered as cards with action buttons. Long text is rendered as formatted markdown.

You can say profile 1 to switch Chrome to Profile 1, profile 2 gemini to open Gemini in Profile 2, or flight 1 mitos to send the first flight result to the MITOS display.

Browser Page

The Browser page at /browser shows the live VNC view alongside a sidebar of your saved sites grouped by profile. Click any site to open it in Chrome on the VNC desktop, using that site's assigned profile. The URL bar at the top lets you type any URL and open it directly.

Sites Page

The Sites page at /sites manages which sites are assigned to which Chrome profile. Each site has a name, URL, login URL, and profile assignment. You can add a site to all 5 profiles at once using the "ALL Profiles" option — useful for sites like Gmail or Gemini where you want one login per profile.

The "Open Login in VNC" button opens Chrome to that site's login page using the correct profile. Log in manually in the VNC viewer — sessions save automatically when Chrome is closed gracefully (SIGTERM).

Worker

The Worker page at /worker shows background browser jobs — multi-step automation tasks that run while you do other things. A job can browse multiple pages, extract data, fill forms, and return a structured result. Jobs are defined in JSON with a list of steps: goto, click, type, extract, gemini, screenshot.

Mobile & Overlay

The mobile interface at /mobile is a full-screen chat interface optimised for phones. It supports the same commands as the main agent page including profile switching and flight shortcuts.

The RC overlay at /overlay/rc is a compact panel designed for a second screen or small display. It shows incoming results, approval requests, and job status in real time via SSE. The big overlay at /overlay/big is designed for a TV or large display — results appear in large readable cards.

The popup overlay at /overlay/popup is a browser extension-style popup — a small floating window you can keep open on any screen to see and send messages without switching tabs.

Gemini Browser Search

This is JARVIS's most powerful search feature. Instead of calling an API (which has rate limits and stale training data), it opens a real Chrome browser, navigates to gemini.google.com/app, types your query into the chat box, and reads the response back. Because it uses a real Google session, it can access Gemini's web search grounding, get today's news, real prices, live flight data, and current weather.

The Gemini profile directory is /root/ai-browser/profiles/gemini — a dedicated Playwright persistent context. This is separate from the 5 Chrome VNC profiles. You need to log into Gemini once through the Sites page (Open Login in VNC → gemini profile) and after that all automated searches use that logged-in session.

Up to 5 Gemini API keys can be configured in Setup for rotation — if one hits its rate limit, the next is used automatically with a staggered cooldown timer.

Genspark Agents

JARVIS integrates with Genspark — an AI super-agent platform — via a permission-gated webhook system. Because Genspark requires your login session, it is disabled by default and must be explicitly enabled before any agent can be triggered. This prevents accidental use.

How to enable: There are three ways to unlock Genspark access:

  • Toggle the Genspark switch in the Sites page
  • Send a webhook: POST http://192.168.0.8:8080/webhook/Genspark/enable
  • Type genspark on in the overlay or agent chat

Calling an agent via webhook:

Content-Type: application/json

Genspark API key: If you have a Genspark API key, add it to Setup → API Keys as GENSPARK_API_KEY. When set, JARVIS routes Genspark agent calls directly through the API instead of using the browser — faster, no login required, and works headlessly. The API key is stored in config/.env and loaded automatically on server restart.

The Overlay popup at /overlay/popup has a dedicated Genspark tab — you can see the current lock status, pick a mode, and run tasks directly without needing to use webhooks.

MITOS Physical Display

MITOS is a 500×500 pixel physical screen running at http://192.168.0.3:9050. JARVIS can push content to it via POST requests to its API. Supported content types: text (plain message), info (formatted info card), link (URL with title), cli (monospace output), full-txt (multi-line text), calendar (calendar event).

From the agent page you can say flight 1 mitos to send the first flight result to the MITOS screen. The Agent page has a dedicated MITOS action bar on each result card with quick-send buttons.

Telegram Notifications

Configure a Telegram bot token and chat ID in Setup to receive notifications. JARVIS sends Telegram messages when: a background job completes, a webhook search returns a result, an approval is needed (guardrail trigger), or an error occurs. The Telegram bot can also be used to send commands to JARVIS — configure the webhook URL on your bot to point to /webhook/receive.

Proxmox VM Fleet (Future)

The current setup runs all 5 Chrome profiles on one machine. When more capacity is needed, the plan is to offload profiles 1–4 to separate VMs running on Proxmox, each one a clone of this VM.

Each VM is a lightweight clone — same Debian base, same JARVIS stack, but only running Chrome and VNC (no AI models). The AI stays on this main VM. When a profile is requested, this VM starts the relevant Proxmox VM via API, waits for it to boot, then routes the Chrome open command to that VM's JARVIS agent.

VMs that are not in use are automatically suspended (paused to RAM — uses about 5% CPU and RAM, wakes in under 2 seconds) or hibernated (saved to disk — zero RAM, wakes in ~10 seconds) based on the idle settings configured in Setup. The idle timeout and idle action (suspend / hibernate / shutdown) are fully configurable per VM slot.

To set up: go to /setup → Proxmox VM Fleet → enter Proxmox host IP, API token, and for each profile slot the VM IP and VM ID. Save. JARVIS handles the rest automatically — boot on demand, idle after inactivity, route VNC stream to the browser.
